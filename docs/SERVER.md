# Server operations and migration

## Architecture

```text
Client -- HTTPS/WSS 443 --> reverse proxy --> HTTP 3097 --> .NET service --> MariaDB
Client -- UDP 3478 and 49160-49200 --> router --> authenticated coturn relay
```

The HTTP reverse proxy does not carry UDP gameplay traffic. MariaDB is accessible only inside the Docker network. The service and relay share a TURN secret to issue time-limited credentials. The relay template restricts allowed peers. All addresses below are placeholders; retain real deployment values only in private operator records.

## Installation

1. Publish `work/zero-hour-services/GenOnlineService/GenOnlineService.csproj` with .NET SDK 10, Release, runtime `linux-arm64`, into `deployment/publish`. Use the matching architecture for a different server.
2. Copy `deployment/.env.example` to `.env`, and `appsettings.example.json` to `appsettings.json`. Generate database/root/JWT/TURN secrets. Match the database password in both files. Generate an invitation separately and store only its SHA-256 hash in `PrivateService:InvitationSHA256`.
3. Set `SERVICE_LAN_IP`, `TrustedProxies`, `WebSocketUrl` and `NativeClientCRC32`. Trust only the actual reverse proxy, checking the source IP observed through Docker. Read the binary CRC from the release's `Version.json`; do not disable this compatibility check.
4. The default `deployment/data/serviceconfig.json` uses direct connections with relay fallback. `relay_all_traffic=true` can be used for a deliberate relay test; restore the intended operating mode afterward.
5. Run `docker compose --project-directory deployment build`, then `docker compose --project-directory deployment up -d db`. `schema.sql` is imported only for an empty database. Review migrations for existing databases; never delete a populated volume to force import.
6. Mount secret configuration read-only. Ensure the unprivileged container account can read it; the ASP.NET image's `APP_UID` was 1654 in the tested deployment. Use restrictive host permissions and verify Docker Desktop mount behavior. Start the service with `docker compose --project-directory deployment up -d service`.
7. Configure coturn using the supplied template, replacing the shared secret, public/container IP and allowed peer addresses. The tested image was `coturn/coturn:4.18.0-r0`, with `-c /etc/coturn/private.conf`, a read-only config mount, unchanged UDP port mappings, restart policy `unless-stopped`, 256 MiB memory and 0.5 CPU. Verify the container address or use a dedicated network. The template is IPv4; IPv6 peers remain denied.
8. Configure HTTPS/WSS and UDP forwarding, then verify externally.

## Reverse proxy and relay

Use a valid TLS certificate for your host, for example `game.example.org`. Forward HTTPS port 443 to the service's HTTP port 3097. Set WebSocket headers `Upgrade: $http_upgrade` and `Connection: $connection_upgrade`, HTTP/1.1, connection timeout 60 seconds and read/write timeouts 3600 seconds. Keep client certificate verification enabled.

Forward UDP 3478 and 49160-49200 to the relay host, preserving port numbers. A public IP change requires updating both `external-ip` and matching `allowed-peer-ip` in coturn; DDNS alone does not update them. Container-IP changes also require reconciliation. Restarting the relay can interrupt active matches; schedule that separately. Automatic IP tracking is not implemented.

## Access and limits

`GuestSession` validates an invitation and creates a private guest session. Each sign-in currently creates a new guest; the implementation caps these accounts at 1000 and responds with HTTP 503 at capacity. Persistent player profiles and guest retention/cleanup are not implemented. Do not bulk-delete accounts when their match history must be retained.

Keep invitations, JWT/database/TURN secrets and live host details outside Git. Session tokens and TURN permissions are generated by the service. Publishing client binaries does not authorize unrelated network changes and does not change the live service.

## Verification

Create a private mode-0600 JSON file outside this checkout containing `invitation` and `turn`. Use the version manifest for the actual accepted client:

```sh
dotnet run --project work/proxy-check -- /private/secrets.json /private/Version.json https://game.example.org
python3 work/check_public_relay.py --secrets /private/secrets.json --host game.example.org --denied-peer 192.0.2.10
```

The API check creates a guest. The relay test allocates two ports, checks the public mapping and denied peers, exchanges ten packets in each direction and releases allocations. Test from another Internet connection: NAT loopback alone does not establish outside reachability. Also run a real two-Mac lobby → start → match → finish test with the final client build.

## Backup, updates and rollback

Before changes, back up configuration, Compose files and a consistent MariaDB dump. Source code is not a database backup. Coordinate DNS/certificate, WSS URL, proxy target, TURN public/container IP, allowed peers, NAT and launcher address during a move. Transfer secrets securely or rotate them consistently across dependent services.

For client releases, coordinate the same binary on every Mac and set its CRC in the service. The automatic client updater does not perform this server rollout. To roll back, restore previous configuration and client binaries, then restart only affected services. Retain database volumes. HTTPS and UDP forwarding can be disabled independently.

## Match diagnostics

Enable `Diagnostics:Enabled` in the service configuration. The deployment template
stores structured JSON Lines in `/app/Diagnostics` on a dedicated Docker volume.
Events include UTC timestamps and a process boot ID, lobby/match/player IDs,
client-reported direct/relay connection outcomes, WebSocket connection duration
and close codes, match assignment, lobby state transitions, reconnects and player
results. Player IDs are numeric correlation identifiers, not anonymized identities.
The new diagnostic stream does not include player names, IP addresses, chat,
request bodies, invitation codes, tokens or exception messages. Existing console
logs are separate and may contain operational identifiers.

Every 30 seconds a health event records process CPU use (100% means one full CPU
core), resident memory, online users, lobby count, sampler scheduling delay and
the cumulative number of dropped diagnostic events. Non-WebSocket controller
requests taking at least 500 ms, or failing with HTTP 5xx, are recorded with the
controller name, status and elapsed time. No raw URL, query or headers are stored.

Defaults are 4 MiB per file, at most 8 files and 7 days retention. Files rotate on
size, UTC date or process restart; expired files are removed on rotation. The
bounded queue never blocks game requests. Storage failures drop events and emit a
console warning; `dropped_events` is reported when storage recovers. Keep the
diagnostic volume private and never include it in public source or release assets.

```json
"Diagnostics": {
  "Enabled": true,
  "Directory": "/app/Diagnostics",
  "MaxFileBytes": 4194304,
  "MaxFiles": 8,
  "RetentionDays": 7
}
```

Read the files through SSH and Docker, or copy only the relevant files into a
private operator directory. Filter by `match`/`lobby`, then compare both players'
connection events with `health` and slow requests at the same UTC time. Do not
expose a public log-download endpoint. The volume survives service replacement;
include it explicitly in operator backups when retaining evidence matters.

These records work with v0.3.3 clients, but do **not** measure gameplay RTT, packet
loss, client FPS or lockstep stalls: peer gameplay traffic does not pass through
the HTTP service. `socket_disconnected` concerns the service WebSocket, not proof
of a failed gameplay connection. Full stutter attribution still needs client
timing/transport samples from the affected match. Automated tests validate log
schema, retention, rotation and shutdown flushing; they do not reproduce a match
between separate Internet connections.

## Multiple native client builds

The service supports `PrivateService:AcceptedClients`, a JSON
object mapping each accepted executable CRC32 (decimal key) to a nonzero shared
simulation CRC32 (decimal value). Only group builds after deterministic replay
and real match verification. Binary admission remains mandatory and unknown
binaries, malformed entries, and protocol mismatches fail closed. While an
explicit mapping exists, `NativeClientCRC32` is not an additional bypass.

The server returns the selected seed only after a successful version check. The
client includes the normal engine version and multiplayer script data in the
final handshake checksum. This permits different platform binaries without
silently ignoring mismatched scripts. It cannot prove simulation determinism.
An absent mapping preserves the existing single-build configuration. Keep the
live server on its validated settings until the complete candidate is accepted.
